# FR-01: Product List

**Branch:** `feature/FR-01`

## Overview

This feature introduces the product list screen, which displays each product's image, name, price and rating. The implementation follows a layered architecture built around four components: model, impl, repository and provider. Each layer has a single responsibility, which keeps the data flow predictable and the code easy to maintain and test.

## Architecture

### 1. Model

The `Product` model is defined using `freezed`, which provides immutability, value equality and `copyWith` support. The abstract class is generated using Claude Code, and the generated code is produced by `build_runner`. The model represents the data returned by the API and holds the fields required by the UI: image, name, price and rating.

### 2. Impl

The impl defines the blueprint of the methods used to communicate with the API. It declares what the application can request from the backend, such as fetching the list of products, and encapsulates the details of each API call. This keeps request logic in one place and separate from the rest of the application.

### 3. Repository

The repository acts as the layer between the impl and the API. It exposes product data to the rest of the application through a clean interface, so upper layers do not depend on how the data is fetched. If the data source changes, only the repository and impl need to be updated.

### 4. Provider

The provider retrieves data from the repository and manages the screen state, including loading, success and error. It notifies the UI whenever the state changes, so the screen rebuilds automatically with the latest data.

### 5. Product Screen

The product screen consumes the provider and renders the product list. Each item displays:

- **Image**
- **Name**
- **Price**
- **Rating**

## Data Flow

1. The product screen requests data from the provider.
2. The provider calls the repository.
3. The repository uses the impl to call the API.
4. The API response is mapped to the `Product` model.
5. The provider updates its state and the screen displays the products.

## Design Summary

The feature uses a layered architecture that separates data, API access and presentation. The model defines the data, the impl declares the API methods, the repository connects the impl to the API, the provider manages state, and the screen displays the result. Each layer depends only on the layer beneath it.

## Benefits

- **Separation of concerns:** each layer has one responsibility, so changes stay localised.
- **Maintainability:** API changes affect only the impl and repository, not the UI.
- **Testability:** each layer can be tested or mocked independently.
- **Immutability and safety:** `freezed` models prevent accidental mutation and reduce boilerplate.
- **Scalability:** new features can reuse the same structure.
- **Consistent UI state:** the provider keeps loading, success and error states in one place.
